# Chapter 3: Storage engines, indexing and data modeling

How a database stores data decides which writes are fast and which queries are cheap. Pick a store by its access pattern, then name its keys and indexes. Deeper reading: DDIA chapters 2 and 3.

## 3.1 The two storage engine families

**B-tree (Postgres, MySQL):**
- Data lives in fixed-size pages (8 KB in Postgres) arranged as a balanced tree.
- Every change is first written to a write-ahead log (WAL) for durability. Pages are flushed to disk later.
- A lookup touches about 3 to 4 pages, even across hundreds of millions of rows.
- Writes hit random pages, and each write lands twice: in the WAL and in the page.

**LSM-tree (Cassandra, Scylla, RocksDB):**
1. A write is appended to a commit log and inserted into an in-memory table (the memtable).
2. When the memtable fills, it is flushed to disk as an immutable sorted file (an SSTable).
3. Background compaction merges SSTables and drops overwritten values and deleted data.
4. A read checks the memtable, then SSTables from newest to oldest. A Bloom filter per SSTable skips files that can't hold the key.

|                 | B-tree                      | LSM-tree                      |
|-----------------|-----------------------------|-------------------------------|
| Writes          | Slower, random I/O          | Very fast, sequential         |
| Point reads     | Fast and predictable        | May check several files       |
| Range scans     | Excellent                   | Good within a partition       |
| Background cost | Vacuum (Postgres)           | Compaction                    |
| Best for        | Mixed OLTP, complex queries | Write-heavy, key-based access |
| Examples        | Postgres, MySQL             | Scylla, Cassandra, RocksDB    |

Compaction strategies trade write cost against read cost. Size-tiered favours writes. Leveled favours reads. Time-window compaction suits time-series data with TTLs, because whole files expire together.

**The tombstone gotcha.** A delete in Cassandra or Scylla writes a marker called a tombstone, which lives until compaction removes it. Using a table as a queue (insert, then delete) piles up tombstones. Reads then scan thousands of them and time out.

> **my notes:**
> - simplest way to remember: btree updates in place, lsm never updates in place, just appends and cleans up later. thats why lsm writes are cheap and reads/compaction pay for it
> - we have both, pg/aurora + scylla. so this is basically why scylla for high write stuff and pg for everything relational
> - tombstones: if something needs queue behaviour, use redpanda/celery, not a scylla table with deletes
> - TTL heavy time series data in scylla -> time window compaction

## 3.2 Postgres internals worth knowing

- **MVCC.** An UPDATE writes a new row version and leaves the old one. Readers never block writers.
- **Vacuum.** Old row versions (dead tuples) cause bloat until autovacuum cleans them.
- **Long transactions block cleanup.** One connection stuck "idle in transaction" can bloat the whole database.
- **Wraparound.** Transaction IDs are finite. If autovacuum can't keep up, Postgres eventually stops accepting writes to protect data. This has caused famous outages.
- **HOT updates.** If an update changes no indexed column, Postgres skips index updates. Each extra index makes more updates expensive.
- **Connections are processes,** each costing several MB of memory. Use a pooler like PgBouncer. Its transaction mode breaks session features such as SET and session-level advisory locks.

> **my notes:**
> - update in pg = insert new version + mark old one dead. so update heavy tables bloat fast if vacuum lags
> - django angle: a `transaction.atomic()` block that does slow work inside (external api call, big loop) holds the txn open = same "idle in transaction" problem. keep atomic blocks short, do network calls outside
> - same for celery tasks that open a txn and then wait on something
> - HOT updates are a good reason not to index columns that change a lot (status, counters, last_seen etc) unless really needed
> - aurora has different storage underneath but MVCC + vacuum + wraparound still apply
> - pgbouncer transaction mode + django needs `DISABLE_SERVER_SIDE_CURSORS = True`

## 3.3 Indexes

An index is a separate structure mapping a key to row locations. It speeds reads and slows every write.

| Index type       | Supports                   | Use for                                 |
|------------------|----------------------------|-----------------------------------------|
| B-tree (default) | Equality, ranges, ORDER BY | Almost everything                       |
| Hash             | Equality only              | Rarely worth it over B-tree             |
| GIN              | Contains-style lookups     | JSONB, arrays, full-text search         |
| GiST             | Overlap and nearness       | Geospatial data, time ranges            |
| BRIN             | Coarse block ranges        | Huge append-only tables ordered by time |

**Composite indexes follow the leftmost prefix rule:**
- An index on (a, b, c) serves queries on a, on a, b, and on a, b, c. It does not serve b alone.
- Put equality columns first, then the range or sort column.
- For `WHERE user_id = ? ORDER BY created_at DESC`, index (user_id, created_at). The database reads rows already in order and stops after the limit.

**Specialised variants:**
- Covering index (INCLUDE extra columns) answers the query from the index alone, an index-only scan.
- Partial index (`WHERE status = 'PENDING'`) stays small and hot when you only ever query a subset.
- Expression index (`lower(email)`) supports case-insensitive lookups.

**Operating indexes on the job:**
- A column with few distinct values, like a boolean, rarely helps as an index on its own.
- Read plans with EXPLAIN ANALYZE. Estimated rows far from actual rows means stale statistics; run ANALYZE.
- On a live table, use CREATE INDEX CONCURRENTLY. The plain version blocks writes for the whole build.
- Find unused indexes in pg_stat_user_indexes and drop them; they only cost writes.

> **my notes:**
> - composite index = phone book sorted by (last name, first name). easy to find by last name, useless if you only know first name
> - rule of thumb: equality cols first, then the range/sort col
> - all of these work in django `Meta.indexes`: partial -> `models.Index(fields=[...], condition=Q(...))`, covering -> `include=[...]`, expression -> `models.Index(Lower("email"), name=...)`
> - for big live tables use `AddIndexConcurrently` from `django.contrib.postgres.operations`, migration needs `atomic = False`. normal AddIndex locks writes during the build
> - `queryset.explain(analyze=True)` gives the plan straight from django shell

## 3.4 Relational data modeling

- Normalize first so each fact lives in one place. Denormalize on purpose for hot read paths, and own the code that keeps copies in sync.
- Let constraints enforce invariants. UNIQUE(show_id, seat_id) makes double-booking impossible at the storage layer, whatever bugs the code has.
- JSONB fits sparse or variable attributes, indexed with GIN. Keep fields you filter, join or sort on as real columns.
- Money is never a float. Store integer paise or use NUMERIC.
- Soft deletes add `WHERE deleted_at IS NULL` to every query. Unique constraints then need a partial unique index.
- Primary keys. Random UUIDv4 keys scatter inserts across the index and hurt locality. Time-ordered IDs like UUIDv7, ULID or Snowflake keep inserts sequential. Chapter 12 goes deeper.
- Timestamps are stored in UTC as timestamptz.

> **my notes:**
> - app level checks have race conditions (two requests check, both see "free", both insert). a db constraint can't race. so constraint = last line of defence
> - django: `UniqueConstraint(fields=[...], name=...)`, and with soft deletes add `condition=Q(deleted_at__isnull=True)`
> - money -> `DecimalField` (that's NUMERIC) or int paise. never FloatField
> - `USE_TZ = True` keeps datetimes in UTC
> - JSONField is fine for extra attributes but if i'm filtering on a key all the time it should be a proper column
> - uuid4 PKs = inserts land all over the index. time ordered ids keep inserts at the end

## 3.5 Wide-column data modeling (Scylla, Cassandra, DynamoDB)

- Design from queries. Write down each query first, then make one table per query. There are no joins.
- The partition key decides which node holds the data and what is stored together.
- The clustering key decides the sort order inside a partition.
- Example. For "latest 50 messages in a chat," partition by chat_id and cluster by message_id DESC. The query becomes one contiguous slice.
- Bound every partition. A busy group chat grows forever, so bucket by time: partition key (chat_id, month). Keeping partitions under about 100 MB is a common rule of thumb.
- Avoid hot partitions. One celebrity key overloads one set of replicas, however big the cluster is.
- Ad-hoc queries don't work. Secondary indexes and materialized views are limited, so you maintain extra query tables yourself.
- Lightweight transactions (compare-and-set) exist but run a consensus round, so they are much slower than normal writes.

> **my notes:**
> - mindset flip from pg: in pg you model data then write queries. in scylla you write queries first then model tables around them
> - partition key = where it lives, clustering key = how it's sorted inside
> - same data in 2 tables for 2 queries is normal here, not a smell. but the app has to write both
> - unbounded partition = problem that shows up slowly. add a time bucket to the partition key early
> - hot partition: more nodes don't help since one key always maps to the same replicas
> - LWT (`IF NOT EXISTS`) only where correctness really needs it, it's slow

## 3.6 Other store types

| Type            | Examples                  | Reach for it when                            |
|-----------------|---------------------------|----------------------------------------------|
| Key-value       | Redis, DynamoDB           | Lookup by key, caching, counters             |
| Document        | MongoDB                   | Flexible nested records read as a whole      |
| Wide-column     | Scylla, Cassandra         | Huge write volume, time-ordered data per key |
| Search          | Elasticsearch, OpenSearch | Full-text search and relevance ranking       |
| Time-series     | Prometheus, TimescaleDB   | Metrics and monitoring                       |
| Columnar (OLAP) | ClickHouse, BigQuery      | Aggregates over billions of rows             |
| Graph           | Neo4j                     | Multi-hop relationship queries               |
| Blob            | S3, GCS                   | Images, video, files                         |

**Row vs column storage.** Row stores (Postgres) suit transactions on individual records. Column stores (ClickHouse) suit scanning a few columns across many rows. Never run heavy analytics on your production primary.

> **my notes:**
> - row store = good at "give me this one record". column store = good at "sum this one column over 1B rows"
> - heavy reports should hit a read replica or an analytics copy, never the primary
> - redis = cache/counters/rate limits, not source of truth

## 3.7 Choosing a store

- Default to Postgres until a specific requirement breaks it. It scales further than most people assume, through vertical scaling, read replicas, native table partitioning and extensions like Citus.
- Move to wide-column for write volume beyond one primary, simple key-based access, very large data, or multi-region writes.
- Use a system of record plus derived stores. Search indexes, caches and analytics copies are fed from the main database, usually through CDC (Chapter 9).
- Justify by access pattern, not brand. "Scylla because we write 200K messages a second and always read by chat" beats "Cassandra because it scales."
- When proposing a design, name the store, its keys and its indexes (e.g. messages in Scylla, partition key (chat_id, month), clustered by message_id DESC), state the query each choice serves, and call out the operational cost: compaction, vacuum, hot partitions or index write cost.

> **my notes:**
> - default answer is pg. move only when there's a specific reason (write volume, key based access, data size, multi region)
> - one source of truth, everything else (cache, search, analytics) is derived from it
> - template for explaining a choice: store + keys/indexes + the query it serves + what it costs to run
> - "X because it scales" is not a reason. "X because of this write rate + this access pattern" is
