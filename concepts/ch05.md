# Chapter 5: Caching

A cache is a fast, temporary copy of data kept close to where it's needed, so you don't recompute or re-fetch it. Caching is the most common fix in HLD and the most common source of subtle bugs.

## 5.1 Key terms

- **Hit / miss:** the data was in the cache, or it wasn't and you had to go to the source.
- **Hit rate:** the share of requests served from cache. Below about 80% for a hot path, question whether the cache earns its cost.
- **TTL (time to live):** how long an entry stays before it expires on its own.
- **Eviction:** the cache throwing entries out because it's full.
- **Stale data:** a cached value that no longer matches the database.
- **Working set:** the subset of data that's actually requested often. You only need to fit this in memory, not everything.

> **my notes:**
>
> - working set is the key idea. don't need to cache the whole table, just the hot part
> - hit rate is visible in redis `INFO stats` (keyspace_hits vs keyspace_misses). worth checking before adding more caching anywhere
> - low hit rate = paying for an extra network hop on most requests for nothing

## 5.2 Where caches live

| Layer       | Example                           | Speed                          | Watch out for                                    |
| ----------- | --------------------------------- | ------------------------------ | ------------------------------------------------ |
| Client      | Browser or app cache              | Fastest, no network            | You can't invalidate it remotely                 |
| CDN         | CloudFront, Cloudflare            | Very fast, near the user       | Only for shareable, mostly public data           |
| In-process  | A hash map or LRU inside your app | Nanoseconds                    | Each instance has its own copy; they drift apart |
| Distributed | Redis, Memcached                  | About 0.5 ms (one network hop) | A shared dependency that can fail                |
| Database    | Postgres buffer pool              | Automatic                      | You don't control it directly                    |

A common setup has two levels: a tiny in-process cache for the hottest keys, in front of Redis, in front of the database.

> **my notes:**
>
> - each layer = faster but harder to invalidate. client cache is fastest and you basically can't take it back once it's out
> - in-process cache with multiple pods on k8s = every pod has its own copy, so after an update some pods serve old data till their TTL runs out. ok for config/static stuff, not for user data
> - django `LocMemCache` is exactly this (per process), redis cache backend is the shared one
> - "redis is a shared dependency" -> if redis goes down, does the app fall back to db or crash? should check how our code handles a cache error

## 5.3 Read and write patterns

| Pattern               | How it works                                                      | Pros                                                           | Cons                                        | Use for                            |
| --------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------------- | ---------------------------------- |
| Cache-aside (default) | App checks the cache; on a miss, reads the DB and fills the cache | Only caches what's used; a cache outage just makes things slow | First request always misses; can go stale   | Most read paths                    |
| Read-through          | The cache library loads from the DB on a miss                     | Simpler app code                                               | Same as cache-aside                         | When your library supports it      |
| Write-through         | Every write goes to cache and DB together                         | Cache stays fresh                                              | Slower writes; caches data nobody reads     | Data read right after it's written |
| Write-behind          | Write to cache now, flush to DB later in batches                  | Very fast writes                                               | Data lost if the cache dies before flushing | View counts, likes, analytics      |
| Write-around          | Write only to the DB and delete the cache key                     | Simple, avoids caching cold data                               | Next read misses                            | Pairs with cache-aside             |

> **my notes:**
>
> - cache-aside + write-around (delete on write) is the default combo. pretty much what django's `cache.get_or_set(key, fn, timeout)` does on the read side
> - write-behind = redis is temporarily the source of truth. only for data where losing a few seconds is fine. eg INCR counters in redis + celery beat job that flushes to pg every minute
> - write-through only makes sense if the data is read right after it's written, otherwise just filling memory

## 5.4 Invalidation

**Rule:** update the database, then delete the cache key. Don't set it. If two writers each SET their new value, they can finish in the wrong order and leave the older value cached forever.

Deleting still has a rare race:

1. A reader misses and reads the old value from the database.
2. A writer updates the database and deletes the cache key.
3. The reader writes the old value into the cache. It's now stale.

Mitigations, from simplest to strongest:

- **Always set a TTL.** It caps how long any bug can last.
- **Delayed double delete.** Delete the key again about a second after the write.
- **Versioned values.** Store a version with the value and refuse to overwrite a newer version.
- **CDC-driven invalidation.** A process reads the database's change log and deletes the affected keys (Chapter 9).

> **my notes:**
>
> - delete is safe to repeat and order doesn't matter. two SETs racing can leave the older value in the cache
> - django gotcha: if i delete the key inside `transaction.atomic()` before commit, a reader can refill the cache with the old value before the commit happens. use `transaction.on_commit(lambda: cache.delete(key))`
> - delayed double delete is easy with celery: `apply_async(countdown=1)` for the second delete
> - TTL on every key, no exceptions. it's the safety net for every bug in this section
> - CDC option ties into redpanda (ch 9)

## 5.5 Failure modes

| Problem                    | What happens                                                            | Fixes                                                                                                                          |
| -------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| Stampede (thundering herd) | A hot key expires; thousands of requests miss at once and hammer the DB | Let one request rebuild while others wait (a lock with SET NX); refresh before expiry; serve stale while one request refreshes |
| Penetration                | Requests for keys that don't exist always miss and hit the DB           | Cache "not found" briefly; put a Bloom filter in front                                                                         |
| Avalanche                  | Many keys expire at the same moment, or the cache cluster dies          | Add random jitter to TTLs; run replicas; limit DB load with a circuit breaker                                                  |
| Hot key                    | One key overloads a single Redis node                                   | In-process cache for that key; copy it as key#1 to key#N across nodes                                                          |
| Big key                    | One huge value slows the whole Redis instance                           | Split or paginate large values                                                                                                 |

**Why big keys hurt:** Redis runs commands one at a time on a single thread. One slow command on a huge list delays every other command on that instance.

> **my notes:**
>
> - stampede vs avalanche: stampede = one hot key expires, avalanche = lots of keys expire together (or redis dies)
> - avalanche is easy to cause by accident: bulk job that caches 1 lakh keys with the same TTL = all expire in the same second. add jitter, eg `timeout = 3600 + random.randint(0, 300)`
> - stampede lock = `SET lock:key 1 NX EX 10`. whoever gets it rebuilds, others wait a bit or serve stale
> - penetration: cache a "not found" marker for a short TTL so missing ids don't hit the db every time
> - big keys: `redis-cli --bigkeys` finds them. also never run `KEYS *` in prod, it blocks the single thread. use `SCAN`

## 5.6 Eviction

- **LRU (least recently used):** evict whatever hasn't been touched longest. A good default.
- **LFU (least frequently used):** evict whatever is used least often. Better when some keys are steadily popular.
- **Production gotcha:** Redis's default maxmemory-policy is noeviction. When memory fills, writes start failing instead of old keys being evicted. Set allkeys-lru or allkeys-lfu for a cache.

> **my notes:**
>
> - check what our redis `maxmemory-policy` actually is (`CONFIG GET maxmemory-policy`). managed redis can have a different default than open source
> - careful: if the same redis instance is also a celery broker or holds locks, allkeys-lru can evict those too. eviction policy is per instance, not per db number, so cache and broker should be separate instances
> - LFU better when some keys are popular all the time, LRU fine otherwise

## 5.7 Redis beyond simple caching

| Data structure | Typical use                                    |
| -------------- | ---------------------------------------------- |
| String         | Cached values, counters (INCR), locks (SET NX) |
| Hash           | An object's fields, like a user profile        |
| Sorted set     | Leaderboards, top-K, scheduling by timestamp   |
| Set            | Unique members, like who liked a post          |
| HyperLogLog    | Approximate unique counts in about 12 KB       |
| Stream         | A lightweight message log                      |
| Geo            | Nearby search by latitude and longitude        |

- **Durability options.** RDB snapshots periodically, and AOF logs every write. Both can still lose recent writes.
- **Replication is asynchronous.** On failover, the newest writes can vanish. Never make Redis the only copy of money or orders.
- **Lua scripts run atomically,** so check-and-update logic like rate limits needs no race handling.

> **my notes:**
>
> - sorted set with timestamp as score = simple delayed job scheduler / sliding window rate limiter
> - HyperLogLog for "unique users today" type counts when ~1% error is fine
> - geo could be useful for location based stuff (nearby search)
> - redis = never the only copy of anything that matters (payments, orders, wallet balance)
> - INCR then EXPIRE as two separate calls can race (key with no TTL if the second call fails). lua script or a pipeline fixes it

## 5.8 Describing a cache in a design

- Say what you cache, the key format, the TTL and how it's invalidated. For example: "user:{id} holds the profile JSON, TTL 1 hour, deleted on update."
- Name the staleness you accept. A feed can be a minute old; an account balance can't.
- Raise the stampede risk yourself for any hot key.

> **my notes:**
>
> - template: key format + value + TTL + invalidation + how stale is ok
> - staleness is a product question, not just a tech one. worth asking "how old can this be?" before caching anything
> - any hot key -> mention stampede and the fix up front

> **my answers:**
>
> 1. two writers can race. W1 writes v1 to db, W2 writes v2 to db, W2 sets cache = v2, then W1 sets cache = v1. db has v2 but cache has v1 till TTL. delete has no ordering problem, the next read just loads whatever is in the db. (delete still has the rare reader race, which TTL / double delete handle)
>
> 2. cache stampede. hot key expired, thousands of requests all missed at the same time and all went to the db together. fixes: (a) lock with `SET NX` so only one request rebuilds and the rest wait or get stale data, (b) refresh the key before it expires / serve stale while one request refreshes in the background. also an in-process cache for that one key takes load off redis and the db
>
> 3. ok when losing a few seconds of writes doesn't matter and the data is high volume: view counts, likes, analytics events. dangerous for anything that's a source of truth, like payments, orders, balances, because if redis crashes or fails over before the flush (replication is async) those writes are gone
